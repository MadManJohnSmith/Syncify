Syncify · arquitectura para agentes

Siete oportunidades de profundización

Un inventario de módulos que hoy son superficiales: obligan a conocer su implementación para usarlos. Cada ficha propone una interfaz más pequeña que esconde más, con la evidencia y el coste de no hacerlo. No es un plan de reescritura; es una lista de partes para atacar de una en una.

Base: v0.6.1..dev · 77 commits Fecha: 2026-11-05 Fuentes: git log, GLOSSARY.md, ADR 0001–0009 Solo lectura: ningún candidato implementado

Cómo leer esto

Vocabulario de codebase-design, sin traducciones flojas: un módulo es una unidad con interfaz e implementación; la profundidad es cuánto esconde una interfaz pequeña; un seam es el lugar donde se puede cambiar de implementación sin tocar al cliente; un adapter conecta una implementación concreta a ese seam; leverage es cuántos cambios futuros facilita; locality es que un cambio quede en un sitio.

La prueba de borrado decide: si al borrar el módulo la complejidad desaparece, el módulo era superficial. Si solo se muda a otro sitio, no aportaba profundidad. Las siete fichas son hipótesis: cada una se somete a grilling antes de escribir código; algunas pueden rechazarse.

Las siete fichas

1

SyncOutcome: el saco de 34 campos

Núcleo Rust · src-tauri/src/commands/service.rs

Leverage altoRiesgo medioParte P2

Hoy. La interfaz de los cinco brazos de sync es un struct con 34 campos. Para añadir un contador o un brazo hay que conocer todos los campos, el despacho los vuelve a copiar uno a uno y la semántica de merge cambia según el brazo.

  • service.rs:3313-3348: ArmOutcome con 32 contadores + errors/warnings.
  • Brazos: :3351 SoundCloud, :3604 Deezer, :4199 Spotify, :5044 TIDAL, :6146 Qobuz; todos reciben y devuelven el mismo saco.
  • Despacho :7670-8040: 153 asignaciones de vuelta (138 =, 15 +=); el merge no es uniforme.
  • Política de metadatos repetida 15 veces (p. ej. :3430-3433, :4523-4526) y el closure emit repetido en cada brazo (p. ej. :3360).
trait SyncArm {
    async fn run(ctx: SyncArmContext<'_>) -> Result<SyncOutcome, ArmError>;
}
struct SyncOutcome { /* 34 contadores privados */ }
impl SyncOutcome {
    fn record_import(&mut self, n: u32);
    fn record_metadata(&mut self, c: Completeness);
    fn absorb(&mut self, other: SyncOutcome);
}

Prueba de borrado

Desaparecen las 153 asignaciones y las 15 copias de la política; el merge y la semántica de cada contador quedan en un solo tipo. La complejidad no se muda: se concentra.

Leverage y riesgo

Añadir un contador o un brazo deja de tocar 4,5k líneas. El riesgo es el camino caliente del sync: hay 10 contratos offline y la suite completa como red; la caracterización va delante.

Para un agente. Un trait, un tipo de resultado y un método de merge. Hoy hay que leer el despacho entero para saber qué devuelve un brazo.

EnrichmentEvent: un canal, tres contratos

UI · IPC · ui/src + commands/{library,enrichment}.rs

Leverage medioRiesgo bajoParte P1

Hoy. El canal enrichment-progress transporta tres payloads distintos y cada vista los descifra a mano; además hay invoke crudos aunque exista wrapper.

  • library.rs:1248-1258 emite {status,total,current,enriched,failed,currentTrack}.
  • enrichment.rs:81-87 emite {"type":"lastfm_genre",...}; :312-315 emite EnrichmentJobSummary en camelCase.
  • LibraryView.vue:1240-1268 documenta los tres y los discrimina; MetadataView.vue:2621 declara el payload inline.
  • 9 invoke crudos fuera de api/; 4 son de enriquecimiento: LibraryView.vue:1292, MetadataView.vue:2157, :2640 y :2650. Hay wrappers para enrich_metadata (metadata.ts:213) y enrich_metadata_musicbrainz (:403).
type EnrichmentEvent =
  | { kind: 'musicbrainz'; total: number; current: number; enriched: number; failed: number; currentTrack?: string }
  | { kind: 'lastfm_genre'; message: string }
  | { kind: 'summary'; totalTracks: number; processedTracks: number };

Prueba de borrado

Desaparecen el discriminador de la vista, el tipo inline de Metadata y los cuatro invoke de enriquecimiento. Queda un emisor en Rust y un decoder en ui/src/api/enrichment.ts.

Leverage y riesgo

Cualquier cambio de evento pasa a ser un error de compilación, no una regresión silenciosa. El riesgo es bajo: la puerta de simetría de eventos ya existe; el coste es tocar dos vistas.

Para un agente. El contrato vive en un fichero y la vista consume un composable; no hay que reconstruir el payload leyendo tres productores.

Corrección al implementar P1. El resumen incremental sí tenía consumidor: useIncrementalEnrichment escuchaba el alias del mismo canal y casteaba cualquier payload a EnrichmentJobSummary. El contrato final tipa dos variantes vivas —musicbrainz e incrementalSummary— y retira solo Last.fm, que no tenía listener. Ver PR #150.

DownloadProvider: el orquestador hace de trait

Descargas · src-tauri/src/download/ + crates

Leverage altoRiesgo altoParte P5

Hoy. El orquestador conoce los adaptadores concretos, despacha por string y tiene un caso especial por proveedor. No hay un puerto común; cada adaptador recibe una forma distinta y la cancelación solo se comprueba en una ruta.

  • orchestrator.rs:115-117 guarda Qobuz/Tidal/Amazon concretos; :1438-1450 despacha por string; :2809-2823 trata Amazon aparte; 107 líneas con literales de servicio.
  • Firmas dispares: qobuz.rs:1852-1856 (request + pool), tidal.rs:34-40 (trait local), amazon.rs:226-230 (URL sin DB).
  • DownloadRequest tiene 30 campos (progress.rs:827-871) y Tidal lo re-mapea a 17 (tidal_pipeline.rs:114-148).
  • Cancelación solo en la ruta SongLink (orchestrator.rs:2664-2688).
trait DownloadProvider {
    async fn fetch(&self, job: &DownloadJobContext, cancel: &CancelToken)
        -> Result<DownloadOutcome, ProviderError>;
}

Prueba de borrado

Desaparecen el despacho por string y el caso Amazon; el orquestador deja de conocer la forma de cada proveedor. Añadir un proveedor es registrar un adapter, no editar el match.

Leverage y riesgo

Es el mayor leverage para ADR-0009 (Deezer, SoundCloud, Amazon). El riesgo es alto: cada proveedor tiene rarezas y hay rutas sin tests de integración; exige caracterización por proveedor antes de mover nada.

Para un agente. Un trait muestra el contrato completo; cada proveedor es un fichero autocontenido en vez de una rama de un match de 4,3k líneas.

PlaybackSession: cuatro fuentes sin una sola puerta

Reproductor · commands/player.rs + services/streaming.rs + stream_cache.rs + crates/syncify-player

Leverage altoRiesgo altoParte P6

Hoy. player_load_track es el verdadero orquestador: decide local vs. red, resuelve la fuente, gestiona la caché, numera la generación, hace el prime y arranca el motor. La verificación de cabecera y el flag DASH se filtran hasta la capa de comando.

  • player.rs:312-372: SQL directo a downloads, cálculo de caché, decisión caché completa vs. descarga progresiva.
  • player.rs:469 y :591: spawn_stream_download / spawn_dash_stream_download; :741: guard_stream_frontier desde el ticker.
  • stream_cache.rs:283-298: download_dash(..., on_prime, on_progress) expone la mecánica interna.
  • streaming.rs:1479-1482 verifica cabecera; :70-82 ResolvedStream aún transporta url y is_dash.
impl PlaybackSession {
    async fn open(track: &Track, quality: Quality) -> Result<Self, PlaybackError>;
    async fn read_at(&mut self, offset: u64, buf: &mut [u8]) -> Result<usize, PlaybackError>;
    async fn seek(&mut self, position: Duration) -> Result<(), PlaybackError>;
}

Prueba de borrado

El comando queda delgado; la URL firmada, el DASH, la caché y la generación no cruzan el seam. La complejidad se concentra en una sesión que se puede probar con un proveedor falso.

Leverage y riesgo

Habilita reproductor local, streaming y caché sin que cada uno conozca a los otros. El riesgo es el camino de audio: la puerta automatizada no ejercita audio real ni GUI; hacen falta tests en vivo y una caracterización antes de mover.

Para un agente. Una sola entrada open y un contrato de lectura/seek; hoy hay que seguir cuatro módulos y un ticker para entender qué suena.

Hoy. Tres vistas grandes clonan el mismo comportamiento de lista: mapear el modelo, filtrar, ordenar, paginar, virtualizar y sincronizar la ruta. Cada copia tiene sus constantes y su propia paginación.

  • Mapeo duplicado: LibraryView.vue:1547 y MetadataView.vue:1516 (mismos qualityBucket, availabilitySummary, filePath).

const browser = useTrackBrowser(source, { rowHeight: 56 })
browser.rows      // ya mapeadas, filtradas y ordenadas
browser.total
browser.hasMore

Prueba de borrado

Desaparecen dos mapeadores, tres ventanas virtuales y tres paginadores; la lógica de lista queda en un composable y cada vista declara su fuente. La complejidad se concentra, no se muda.

Leverage y riesgo

Un cambio de orden, selección o scroll se hace una vez. El riesgo es medio: filas agrupadas, reordenación y selección por ids; hay que caracterizar la paridad visual antes de borrar la copia vieja.

Para un agente. Un fichero explica cómo se comporta una lista; hoy hay que comparar tres vistas de ~3k líneas para saber si un cambio es global o local.

DownloadJob: el estado vive en strings SQL

Descargas · download/orchestrator.rs, commands/{queue,library}.rs

Leverage altoRiesgo altoParte P4

Hoy. El estado del job no es un tipo: es una columna de texto consultada en muchos sitios. Cancelar, reintentar y recuperar al arrancar son políticas separadas, sin una máquina de estados que las ate.

  • Predicados dispersos: library.rs:448,587,1148,1711,2172 tratan queued/downloading; queue.rs:2265-2269 cuenta cuatro estados.
  • Cancelar es un UPDATE ... status='cancelled' (queue.rs:2392); reintentar tiene dos presupuestos distintos (queue.rs:2437 retry_count < 99; :2469 < 5).
  • Al arrancar, queue.rs:2546 resetea todos los downloading a queued: la recuperación es un barrido, no una transición.
  • Dos vocabularios de error: el adaptador devuelve mensajes y el orquestador los clasifica para decidir reintento (orchestrator.rs:1536,1602,1641); la cancelación se consulta solo en SongLink (:2664-2688).
enum JobState { Queued, Downloading, Complete, Failed(Reason), Cancelled }
impl DownloadJob {
    fn transition(self, event: JobEvent) -> Result<Self, IllegalTransition>;
    fn cancel(&self) -> CancelHandle;
    fn retry_verdict(&self, now: Instant) -> RetryVerdict;
}

Prueba de borrado

Desaparecen los ~20 predicados de estado, los tres caminos de reintento y el barrido de arranque; las transiciones legales y sus presupuestos viven en un grafo. El token de cancelación sustituye el flag que solo mira una ruta.

Leverage y riesgo

Es la base para P5: el proveedor recibe un contexto estrecho y no decide estados. El riesgo es alto: los strings son contrato con la UI y hay filas legadas; hay que caracterizar cancelación, reintento y recuperación antes de mover nada.

Para un agente. Un enum y un método transition responden qué puede pasar; hoy la respuesta está repartida entre SQL, un flag atómico y funciones de clasificación.

BridgeClient: cada puente reinventa el contrato

Python · scripts/*.py, scripts/services/ y cmd_utils.rs

Leverage altoRiesgo medioParte P3

Hoy. Hay 17 puentes de nivel superior y 16 módulos de servicio. El lanzador genérico existe (tools.rs:339), pero autenticación y ajustes lanzan Python por su cuenta, y cada script repite argparse, captura de stdout, envelope JSON y códigos de salida.

  • Rust: run_bridge_command en commands/tools.rs:339 con 19 llamadas; auth.rs:116-143 construye su propio comando; settings.rs:972-975 hace lo mismo.
  • Python: download_bridge.py documenta el contrato completo (stdout = un JSON, salida incidental a stderr, códigos 0/1/2); auth_bridge.py:42-57, lyrics_bridge.py:50 y metadata_bridge.py:50 lo reimplementan.
  • Seis scripts insertan SCRIPTS_DIR en sys.path; el resto depende del cwd o de un .env. La resolución de herramientas ya vive en cmd_utils.rs:21-331; el protocolo no.
impl BridgeClient {
    async fn call<T: DeserializeOwned>(&self, script: &str, args: &[&str],
        stdin: Option<&[u8]>, timeout: Duration) -> Result<T, BridgeError>;
}

// Python: cada script es un handler, no un CLI
from bridge_protocol import run
def handle(args): ...
if __name__ == "__main__":
    run(handle)

Prueba de borrado

Desaparecen el envelope repetido, los argparse propios y las tres formas de lanzar; queda un cliente Rust y un módulo Python. Cada puente solo declara su handler.

Leverage y riesgo

Habilita P4/P5 y hace que un error de protocolo se arregle una vez. El riesgo es medio: encoding en Windows, Python embebido/venv, secretos por stdin y mensajes de error que la UI ya consume; hay que mantener adaptadores para auth en streaming.

Para un agente. Una interfaz call y un módulo bridge_protocol; añadir un puente deja de ser copiar 80 líneas de ceremonia.

Siguiente paso

No hay ninguna parte aprobada todavía. El proceso es: elegir una ficha, grillarla hasta que la interfaz y el alcance estén cerrados, implementarla en un PR con caracterización, y solo entonces abrir la siguiente. La recomendación es empezar por P1 (EnrichmentEvent): es la más barata, valida el método y mejora de inmediato la navegación de la UI; después P2 (SyncOutcome) y P3 (BridgeClient), que desbloquean el trabajo de descargas.

Estas fichas son hipótesis de diseño, no resultados. La evidencia está verificada contra el árbol, pero ninguna interfaz propuesta se ha compilado ni probado. El grilling puede rechazar una ficha o cambiar su alcance; eso también es un resultado.
